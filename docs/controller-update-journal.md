# Controller update job and recovery journal

`firmware/main/controller_job.c` owns admission and status, independently of the HTTP receiver and the worker's exclusive SPI execution. Status reads copy cached data under the application mutex and perform no controller transactions. Host tests exercise the actual job manager and package validator; they do not establish physical flash reliability or electrical suitability of an uploaded application.

The HTTP receiver first reserves a job. Reservation shares `app.updating` with ESP application updates, so two update types cannot be admitted together. Receiving an incomplete or invalid package does not create a controller mutation intent. Submission validates the exact package length, header, conservative vector layout and complete bank digest. Only a `202` result transfers allocation ownership. The worker borrows the immutable package; the job manager frees it exactly once at terminal completion. Cancellation releases only the matching receiving reservation and cannot cancel an admitted job or another job's reservation.

The worker requalifies the cached source through fresh typed controller observations. No HTTP field chooses a loader source. An arbitrary resident information reply cannot establish fresh loader RAM: an old pending sector can survive there. Admission instead requires a current-boot, single-use proof from the fixed diagnostic sequence or explicit cold-boot recovery below. See the portable loader's reset-boundary requirements.

## Durable intent

Before the core enters or mutates the controller, it persists a versioned 128-byte record under `openkeylight/nxp_job_v1`. The record contains the job ID, source, phase, result, target bank digest, version and role, acknowledged/readback block counts, and mutation-intent flags. Record version2 includes role; earlier version1 records remain readable as production-role records and still block recovery. Its fields have explicit byte offsets and a SHA-256 integrity digest; it contains neither pointers nor compiler-dependent structures. The digest detects corruption, not malicious modification.

The core writes at phase boundaries, not after every 64-byte transfer. Cached counters can therefore be newer than the last durable checkpoint. Both values describe evidence, never an instruction to continue programming.

On startup, absence of the record permits ordinary worker initialization. A pending record, wrong size, bad digest, unknown format, or NVS read failure blocks automatic controller bootstrap, confirmation and output. A pre-commit record cannot reveal whether the commit reached the controller, so reloaded commit intent is reported as `maybe_sent`. No job is reconstructed from the journal and no upload buffer is retained across resets.

Successful installation requires all of the following before journal clearing: complete 448-block programming and readback, verified loader entry, one known-complete commit, the full quiet interval, an established reset boundary, a matching original application observed dark, and the worker's separate typed trial confirmation. Clear/commit failure leaves the running application blocked even when the controller confirmation succeeded. Interrupted and failed mutations never trigger an automatic restore, confirmation retry, or replay of an earlier desired light state.

A separate rejection path handles an unsupported target identified entirely by correlated read-only replies. For example, ordinary legacy 1.3 can answer its version but reject the exact-part getter. That is insufficient qualification to update the controller, but a fully received unsupported response is different from an uncertain transaction. The adapter records this distinction explicitly and marks mutation attempted **before** invoking ownership claim; any claim, output command or loader entry permanently excludes this rejection path for that job.

The rejection path requires a known-idle transport after releasing the worker lease, no persistence failure, and no loader verification, erase/program/readback, commit, Abort, reset boundary or observation in either the saved or returned audit. Only then may it erase and commit the journal. The terminal job is `failed`, with result `invalid`, `recovery_required:false`, `controller_confirmed:false`, and an unsupported-target explanation. It is not installation success. Readiness remains closed until a fresh ordinary bootstrap, and the consumed output revision prevents the previous animation or scene from restarting. A newly accepted Off that was still pending when the job took the lease is retained and attempted once after fresh readiness; an already attempted Off is never retried. A rejected update can be attempted again only as a new explicit request after ordinary readiness returns.

Timeouts, malformed identity payloads, uncorrelated responses, unknown bus phases, any attempted mutation and storage errors remain `recovery_required`. Even an error after journal erasure might have become durable keeps the running application blocked. The rejection proof exists only in the current worker call; a pending journal loaded after a reboot cannot use this path. Thus the API gains no generic journal-clear or uncertain-update retry mechanism.

The API has no generic journal-clearing endpoint. A power cycle alone does not delete the journal or restart a transfer.

## Explicit recovery after physical power cycle

After confirming the ESP firmware, power-cycle the whole light. Within 180 seconds of that fresh boot, an authenticated client may submit `POST /api/v1/controller/recover` with exactly `job_id` and `power_cycle_acknowledged:true`. This acknowledges the physical action; it does not synthesize a reset. Admission requires a valid retained journal, matching job ID, ESP reset reason `POWERON`, no competing job and no earlier recovery attempt. Warm OTA/software resets, malformed or unreadable journals, stale IDs and expired admission windows are rejected. An unconfirmed ESP firmware trial cannot admit recovery.

The blocked worker has not initialized or clocked SPI since startup. The recovery job independently requires a pristine driver, initializes it once, takes the exclusive worker lease and waits 33 seconds without SPI. It then sends one fixed resident information request. An exact response establishes a volatile fresh-resident capability from the acknowledged shared power cycle and pristine bus, rather than from READY-high or information contents alone. The journal remains intact, output stays blocked, and only a **new explicit package upload** can consume that capability. No erase, program, generic memory read, commit, Abort or FD is sent by recovery. No observation is retried.

A narrow alternative handles a loader-entry-only failure when the controller is still the unchanged supported legacy application. The durable record must identify legacy 1.3 and pre-commit failure with zero program/readback and no erase, commit, Abort or complete-bank flag. Only a correlated unsupported/owner-denied information response permits probing exact legacy version 1.3.0.0, claiming once, verifying unsupported original-status getter and actual part `0xbc40`, applying Off once, checking native Off getters, and releasing ownership. After that full synchronized proof, a successful journal erase/commit permits ordinary bootstrap. It does not report installation or optical success, and old output revisions are consumed without replay. A failure anywhere, including journal clearing, stays blocked.

Cached `transport_diagnostic` records the operation stage and result, parsed-response availability, complete raw-body availability, bus phase/READY, routing tag/kind, report metadata and SHA-256. Raw-body availability does not imply a valid envelope/checksum or correlated response. The adapter captures this evidence before cleanup can replace it; it is volatile diagnostic evidence, not a persisted hardware proof. `power_cycle_recovery_available`, `recovery_attempted` and `legacy_reconciled` expose the explicit recovery state without extra SPI activity.

## Explicit off-only diagnostics

An authenticated upload with `X-Controller-Mode: diagnostic-off` admits only a role1 package. Omitting the header admits only role2 production packages. The fixed OFF1 bench profile is version 0.1.0.0, ABI1, qualification flags `0x193`, a 400 ms off-only handoff and an immutable 30,000 ms recovery deadline. This is an explicit bench operation; it is not enabled through the ordinary dashboard upload control.

After complete bank programming, byte-for-byte verification and the protected commit interval, the worker requires fresh matching role1/part/ABI/version/capabilities and native Off state. It never sends trial confirmation FD. It claims the diagnostic application once, verifies its unused OFF1 profile and nonzero generation, then sends the exact OFF1 action once. Missing or uncertain acknowledgements are never retried.

After 550 ms, the worker reads fourteen fixed F1 pages containing 224 big-endian words. It validates all five GPIO/timer snapshots, the off matches, GPIO-before-stop ordering evidence, the same generation and 400–500 ms captured handoff window. A repeated metadata page must match. These checks establish software/register evidence, not optical darkness, nonzero-duty safety or measured real-time bounds.

Only a valid completed record proceeds to 33 seconds of complete SPI silence, covering the profile's 30-second deadline plus the three-second guard. An exact resident information reply then permits the transport to retain a volatile, one-use proof tied to this job. That proof relies on the known-complete commit, observed application and fixed recovery profile; it is not inferred from an arbitrary resident reply. No loader programming, Start or generic memory read occurs between commit and proof creation.

The terminal job remains `diagnostic_trial`, with `controller_confirmed:false`, `recovery_required:true`, output disabled and the journal retained. `registers_verified` and `resident_recovery_ready` distinguish bench evidence and the next-upload capability. A failed bench or resident probe remains an error. A successful bench has no error, but is not production-ready.

A **new explicit package upload** may use that volatile resident proof while the same ESP boot and synchronized bus remain. The new job consumes it once before any loader mutation. Any attempted intervening SPI transfer, unknown bus phase or ESP reboot invalidates it. Receiving or rejecting an invalid package does not consume it. The new job persists fresh intent before proceeding; no interrupted job is resumed and no journal is silently cleared. After reboot, only a separately admitted physical-power-cycle recovery can create a new capability.

Authenticated uploads trust the operator's selected original firmware; package hashes and profile declarations are not signatures. Hardware qualification separately pins the reviewed candidate binary and source. The initial diagnostic path does not expose arbitrary reports, arbitrary memory reads, duty values or FD.

## Verification

Run `python3 tests/controller_job/run_tests.py` with an ASan-capable C compiler and the cJSON development library. The suite uses the real manager and package parser with deterministic NVS, SHA-library and locking boundaries. It covers malformed packages, stale reservations, exactly-once allocation release, every record byte corrupted in turn, truncated records, pending records across simulated reboots, storage/hash failures, ambiguous persistence, and incomplete or unconfirmed terminal evidence. Rejection cases cover each disqualifying mutation/uncertainty flag, retained historical evidence, failed or ambiguous journal clearing and rejection of a reconstructed reboot proof. It also verifies that cached JSON reads issue no NVS operations.

The NVS mock models both a failed commit that leaves the old record and an error after the new record became durable. Atomic storage guarantees, scheduling under load and physical power interruption remain hardware/ESP-IDF qualification concerns.

Diagnostic tests exercise role/mode mismatch, all fixed page failures, malformed profile/ACK/snapshot evidence, no-FD completion, one-shot commands, retained journals, single-use resident admission and loss of proof on reboot. The adapter/core suite executes the complete 448-block programming and readback path plus the bounded OFF1 flow against deterministic hardware boundaries. Native transport tests independently exercise token invalidation on attempted transfers and ambiguous completion. These are offline tests, not a hardware qualification claim.
