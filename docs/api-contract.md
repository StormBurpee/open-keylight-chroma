# API v1 implementation contract

All paths use `/api/v1`. The [OpenAPI 3.1 document](openapi.json) describes the implemented request and response schemas; [Home Assistant integration](home-assistant.md) documents the separate MQTT interface. This is a source contract, not a claim that public installation or every integration has been qualified on hardware.

HTTP uses port 80 on a trusted LAN. JSON requests use `Content-Type: application/json` and are limited to 1–2048 bytes with a ten-second read deadline. Unknown or duplicate fields, embedded NUL and invalid values are rejected before that request is submitted. Firmware string lengths are UTF-8 byte limits. Routes have no query parameters. JSON responses use `Cache-Control: no-store` and close the connection.

Mutations require `Authorization: Bearer <device-token>` except `POST /pair`. `GET /clients` also requires authentication; other documented GET routes are public LAN metadata. `Host` must match the device IP, hostname, hostname with `.local`, or setup address `192.168.4.1`, with an optional `:80`. When present, `Origin` must be exactly `http://` followed by that Host. There is no cross-origin API or TLS listener. Tokens are not URL parameters.

`GET /device`: `{id,name,model,firmware,api_version:1,uptime_ms,network:{connected,rssi,ip},controller:{connected,version,ready,backend,status,part_id,trial_confirmed,last_health_ms},capabilities:{...}}`. Controller `connected` records communication; `ready` means output commands are permitted. Backend is `unknown`, `legacy`, or `original`; status is `starting`, `ready`, `diagnostic`, `unsupported`, or `fault`. `part_id` is the observed original-controller part, or zero when unavailable. `trial_confirmed` concerns the NXP startup trial, separately from the ESP's top-level `trial_pending`. `last_health_ms` is the ESP uptime of the last validated lifecycle response, or zero before validation. None of these fields measures emitted light.

`GET /state`: `{revision,desired:{power,mode,brightness,temperature_k,rgb:{r,g,b},transition_ms,effect,recording_lock},reported:{...same output fields...,valid},operation:{status,error},last_actor}`. `mode` is `white` or `color`; brightness is 0–100; temperature 3000–7000 K; RGB bytes 0–255; transition 0–10000 ms; effect `none`, `aurora`, or `breathe`. Reported output is getter-confirmed where available, not an optical measurement. `operation.status` is `idle`, `pending`, or `error`.

`PATCH /state`: at least one desired field plus optional `expected_revision`, an integer 0–4294967295 matching `GET /state`'s global revision. Every accepted patch increments that revision, including lock-only changes. Optional `X-Keylight-Actor: dashboard|streamdeck|automation` is attribution, not an authorization role. A valid authorized patch returns 202 and the state envelope. A stale revision returns 409 without applying the patch. RGB requires all three channels; RGB alone does not select color mode. Selecting white mode clears the effect unless an explicit incompatible effect makes the patch invalid.

202 means accepted intent. Poll state, inspect the operation and compare getter-supported reported fields before treating an output change as confirmed. A pending command may coexist with a previous valid report. Recording Lock rejects output changes with 423 except Off; unlock in a separate command before changing other output fields. Output changes return 503 while the controller is not ready; lock-only changes remain available. During an ESP upload or controller package reception, commands return 503 except exactly `{"power":false}`, which still requires controller readiness. Once controller installation begins, readiness closes and all output commands are unavailable. Never automatically retry a timed-out mutation: the first request may already have been accepted.

`GET /history`: `{entries:[{sequence,uptime_ms,actor,event,detail}]}` bounded newest-first history.

`GET /scenes`: `{scenes:[{id,name,state}]}` returns saved slots in ID order. `PUT /scenes/{id}` requires exactly `{name,state}`; `state` must include at least one desired field and must not contain `expected_revision`. Omitted fields use factory defaults, **not** the current state. The saved Recording Lock is always cleared. This saves without activating. IDs are 1–8 and names are 1–32 UTF-8 bytes. PUT replaces a slot; no delete endpoint exists.

Focus, Blue hour, Ember and Afterglow are [seeded once into available slots](scenes.md), without replacing existing IDs or activating a scene. A saved collection retains its seeding marker across edits and reboot. Persistence failures return 503; after an ambiguous scene write, reboot reloads the durable collection before another scene edit is allowed.

`POST /scenes/{id}/activate` applies a saved scene and returns 202 with the state envelope. Its body may be absent, `{}`, or `{"expected_revision":n}`. It respects revision checks, Recording Lock and update restrictions. A missing slot returns 404.

`GET /settings`: `{name,role,output_encoding,mqtt:{enabled,uri,username,connected},button:{single:"toggle",double:"next_scene",hold:"pair"}}`. SSID and passwords are omitted; the broker URI and username are public metadata. `PATCH /settings` accepts a nonempty subset of `name`, `role`, `ssid`, `password`, and `mqtt:{enabled,uri,username,password}`. Omitted fields retain their values. Role is `key`, `fill`, `background`, or `other`. Name and SSID are 1–32 UTF-8 bytes; Wi-Fi password is empty or 8–64 bytes; MQTT URI is at most 128 bytes and its username/password at most 64 bytes. Control characters are rejected. Passwords are write-only. Settings persist before 200; Wi-Fi/MQTT fields request a restart. No revision precondition is implemented for settings.

Send `{"output_encoding":"srgb"}` or `{"output_encoding":"linear"}` as a separate settings PATCH, without other fields. The default is `srgb`: display RGB is decoded before output scaling; `linear` treats channel bytes as linear values. White controls are independent. This setting uses its own NVS byte and preserves the existing configuration record and credentials. A successful changed value persists without reboot, increments both state and output revisions, and queues a new render; 200 confirms the setting was saved, not optical output. Poll `/state` for completion. Recording Lock returns 423, an update returns 409, and unavailable readiness or persistence returns 503. Selecting the existing value is a no-op; an update still rejects the request. Missing, unreadable or invalid stored values use the sRGB default without rewriting storage at startup.

`POST /pair`: during the pairing window, exactly `{label}` returns `{token}` once with status 201. The label is 1–32 UTF-8 bytes without control characters. A successful issuance consumes the window. The token is 64 lowercase hexadecimal characters. Closed window, full client capacity or failure to persist it returns 403. A device with no paired clients opens its initial window at application startup.

`POST /update`: authenticated application-only binary upload, with exact `Content-Type: application/octet-stream`, known `Content-Length`, and `X-SHA256` containing the lowercase digest of the complete body. Images must be 288–1572864 bytes and fit the actual inactive application slot. The total upload budget is 120 seconds. The digest detects corruption against the supplied value; it does not authenticate a firmware publisher. Never send a bootloader, partition table, NXP image or merged flash image. Success returns 202 `{accepted:true,rebooting:true}` and schedules a restart. Reconnect and verify the new application before confirming it. A failed or ambiguous upload may have modified the inactive slot; do not automatically retry it.

`POST /controller/update`: authenticated NXP application update. Send one 28,736-byte `.oklnxp` package as `application/octet-stream`, with its complete package SHA-256 in `X-SHA256`. The 30-second receive budget includes the full body and digest check. The fixed header identifies the supported part, ABI, lighting role, version and complete 28 KiB bank digest; the device also validates its vector table. This accepts owner-built firmware, but metadata and checksums do not prove electrical qualification or publisher authenticity. The ESP trial must already be confirmed. The whole package is validated in RAM before a controller job begins; 202 `{accepted:true,job_id}` is admission, not installation success. The worker turns the light off and verifies that state before entering the loader. It does not replay the previous scene after installation. During controller flashing and its quiet interval, even Off and health polls must wait behind exclusive transport ownership.

`GET /controller/update` returns the cached job without touching SPI: `{job_id,state,phase,result,target_sha256,program_blocks_acked,readback_blocks_verified,total_blocks:448,commit_attempted,commit_delivery,quiet_completed,controller_confirmed,recovery_required,error}`. IDs and target digests are null before available; result and error are null when absent. State is `idle`, `receiving`, `queued`, `running`, `completed`, `failed`, or `recovery_required`. Written/read-back counters cover staging only. Completion requires fresh matching application identity, the separate controller startup confirmation, and durable clearing of the update journal. A lost HTTP response must be resolved by inspection, never an automatic resubmission. A fully correlated unsupported target rejected before any ownership or output mutation reports `failed` after its journal is durably cleared; output reopens only after a fresh normal bootstrap. An interrupted or uncertain controller update remains gated after an ESP restart; this version has no public recovery/reset endpoint. See [the journal contract](controller-update-journal.md).

After a safely rejected update, a new Off accepted during package reception and still pending when the worker took the job is attempted once after fresh readiness. Older scenes and already attempted Off commands are not replayed; a newer user revision supersedes that retained Off.

For an explicitly trusted bench image, `X-Controller-Mode: diagnostic-off` selects diagnostic role 1; omitting the header selects lighting role 2. The package role must match. The diagnostic procedure checks the fixed OFF1 profile, sends its bounded off-only command once, and reads the fixed register snapshots. It never sends production confirmation or enables ordinary output. Profile metadata and hashes are not authentication of arbitrary owner-supplied firmware.

Controller status additionally includes `target_role` (1, 2 or null), `diagnostic_trial_observed`, `resident_recovery_ready`, and `diagnostic` (null or `{profile:"OFF1",command_attempted,command_acknowledged,registers_verified,generation,snapshot_words,error}`). The snapshot is exactly 224 unsigned 32-bit words. State `diagnostic_trial` distinguishes an observed diagnostic from a confirmed lighting installation. A successful register check proves register values and software timing, not optical darkness. After the fixed recovery deadline and an uninterrupted quiet interval, a matching resident-loader reply can establish `resident_recovery_ready:true`. That volatile proof admits one subsequent explicit package under the same SPI worker. Any intervening SPI attempt, uncertain transport state or ESP restart invalidates it; the journal is retained until a production installation completes. This is not a general journal-clear or retry endpoint.

Initial legacy migration requires exact controller version 1.3.0.0 and a supported actual-part getter, available in the private diagnostic controller image used for development. Ordinary stock firmware without that getter is rejected before lighting or loader mutation. An exact legacy ownership-denied status can require a verified claim before repeating the read-only identity checks; once a claim is attempted, an update failure retains its recovery journal. Original-firmware updates use the explicit controller status ABI and observed part ID. The package tool is `python tools/package_controller.py --help`; it prepares a file and never uploads it. Diagnostic packaging requires the separate `--role diagnostic` selection.

`POST /confirm`: authenticated acceptance of the current trial application, with no body needed. Success returns 200 `{confirmed:true}` and is idempotent once confirmed. A new image has a 180-second application-level trial. Confirmation and expiry select one terminal decision; failed, expired, concurrent or unavailable confirmation returns 503. The fallback attempts to select the other valid application slot and restart. The installed bootloader has no automatic crash rollback, so this does not protect a failure before the application's fallback code can run. Another OTA upload returns 409 while a trial is pending or an upload is active, preserving the prior slot during an unconfirmed trial.

`POST /pairing`: an already paired client can open one 180-second pairing window. The physical three-second button hold opens the same window. `GET /clients` requires authentication and returns `{clients:[{id,label}]}` without token material. `DELETE /clients/{id}` revokes that client; revoking the current client also ends its access. Tokens are stored as hashes in one atomic NVS record. Holding the physical button continuously for ten seconds beginning at boot revokes all clients while preserving Wi-Fi and scenes.

When disconnected from a configured network, a pairing hold also opens a temporary `Keylight-Setup-…` access point for 180 seconds. Pairing does not shorten that network's lifetime. A light with no configured network remains in setup mode. Connect to that network and open `http://192.168.4.1/`; the System page accepts a new SSID/password and explicitly saves and restarts. Credentials are write-only.

`GET /device` also reports `pairing_open`, `trial_pending`, `free_heap_bytes` and `reset_reason`. Capability booleans are `white`, `color`, `transitions`, `effects`, `scenes`, `settings`, `ota`, `controller_ota`, and `white_transitions`; absent capabilities must not be assumed. `effect_names` is the supported list. `reported.confirmed_fields` identifies which normalized fields are supported by a controller getter. During the compatibility backend's custom RGB rendering, native RGB is not getter-readable and its report is invalidated. Colour output uses a fixed native RGB master of 255, with the selected encoding and brightness applied once to each channel. Even a zero-duration change uses an acknowledged custom frame before parking its exact bytes as Static, avoiding the legacy static-to-static fade. Completion requires fresh raw RGB, master, effect and white-channel getters to match the forward-converted intent; the normalized report then retains the chosen RGB and brightness. See [colour rendering](color-rendering.md) for handoff, reboot reconstruction and quantization limits.

The dashboard polls state and device health at 1 Hz while visible, never beginning a poll during an in-flight mutation. It coalesces continuous controls and keeps at most one mutation in flight. Connection errors retain the last confirmed display and visibly mark it stale. Controller readiness changes disable output controls without blocking settings or update access. Development demo mode is explicit (`?demo=1`) with an always-visible label and entirely separate transport; it is excluded from the production build.

Errors use `{error:"message"}`. Key status codes are 400 for invalid input, 401 for missing/invalid authentication, 403 for host/origin or pairing rejection, 404 for an unknown route/client/scene, 409 for revision or operation conflict, 423 for Recording Lock, and 503 for unavailable persistence/service operations. OTA also uses 408 for receive/deadline failure and 413 for an image outside the allowed size. An error after hardware work does not imply rollback of earlier acknowledged controller commands.
